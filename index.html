1 Introduction

1.1 什么是智能体

在理解任何复杂概念时，从简明定义入手最为有效。在人工智能领域，智能体是指能够通过传感器感知环境，并自主地借助执行器采取行动，以实现特定目标的实体。

这一概念包含四个核心要素：环境、传感器、执行器和目标。环境是智能体所处的外部世界，例如自动驾驶汽车面对的是不断变化的道路交通，而交易算法面对的是高速波动的金融市场。智能体通过传感器持续获取环境信息，摄像头、雷达、麦克风或 API 返回的数据，都是其感知能力的体现。

在获得信息后，智能体需通过执行器对环境施加影响，从而改变其状态。执行器既可以是物理装置，如机械臂或方向盘，也可以是虚拟手段，如执行代码或调用服务。

真正使智能体具备“智能”的关键在于其自主性。它并非简单地被动响应刺激或机械执行指令，而是能够基于感知结果和内部状态进行独立决策，以实现既定目标。由此形成的“感知—决策—行动”闭环，构成了智能体行为的基本机制。

1.1.1 传统视角下的智能体

在大语言模型兴起之前，人工智能领域已对“智能体”展开了数十年的研究。如今所谓的“传统智能体”并非单一形态，而是沿着一条由简入繁、由被动反应走向主动学习的清晰演进路径发展而来。

这一演进的起点是结构最简单的反射智能体。其决策机制基于工程师预先设定的“条件—动作”规则。例如自动恒温器：当传感器检测到室温高于设定值时，便启动制冷系统。

这类智能体完全依赖当前感知，不具备记忆或预测能力，类似数字化的本能反应，虽然高效可靠，却难以处理需要上下文理解的复杂情境。正因如此，一个核心问题随之出现：当仅凭当前状态不足以支撑决策时，智能体应如何应对？

为解决感知受限、目标多样与自主进化的问题，传统智能体经历了从基于模型的反射智能体（用内部世界模型与记忆理解当前状态），到基于目标的智能体（通过规划选择通向目标的行动），再到基于效用的智能体（在多目标间权衡、最大化期望效用），最终发展为学习型智能体（以强化学习通过经验不断优化策略）的演进路径，勾勒出人工智能由被动反应走向自主学习与理性决策的完整脉络。

1.1.2 大语言模型驱动的新范式

以 GPT（Generative Pre-trained Transformer）为代表的大语言模型正在深刻改变智能体的构建方式与能力边界。由大语言模型驱动的 LLM 智能体，在核心决策机制上与传统智能体存在本质差异，因此具备了全新的能力特征。

这种变化可以从核心引擎、知识来源和交互方式等多个维度清晰体现（见表 1.1）。总体而言，传统智能体依赖工程师的显式规则和知识设计，其行为确定且受限；而 LLM 智能体通过海量数据预训练，形成了隐式的世界模型和涌现能力，能够以更灵活、更通用的方式应对复杂问题。

正因如此，LLM 智能体可以直接理解并处理高层次、模糊且富含上下文的自然语言指令。以“智能旅行助手”为例：

在 LLM 智能体出现之前，旅行规划通常需要用户在天气、地图、预订平台等多个应用之间来回切换，自行完成信息整合和决策。而 LLM 智能体可以将这一过程统一完成。当接收到“规划一次厦门之旅”这样的模糊需求时，其工作方式主要体现在：

  • 规划与推理：将高层目标拆解为若干逻辑子任务，如确认偏好、查询信息、制定行程和安排预订，形成模型驱动的内在规划过程。

  • 工具使用：在发现信息不足时，主动调用外部工具补充信息，例如查询天气，并根据结果调整活动推荐。

  • 动态修正：将用户反馈视为新的约束条件，实时调整计划，如在预算变化后重新筛选合适的酒店方案。

整体来看，我们正在从开发单一功能的自动化工具，转向构建能够自主规划、执行与调整的通用问题解决系统。重点不再是具体代码实现，而是如何引导一个通用的“大脑”完成规划、行动与学习

1.2 智能体的构成与运行原理

1.2.1 任务环境定义

要理解智能体的运作，我们必须先理解它所处的任务环境。在人工智能领域，通常使用PEAS 模型来精确描述一个任务环境，即分析其性能度量(Performance)、环境(Environment)、执行器(Actuators)和传感器(Sensors) 。

1.2.2 智能体的运行机制

在定义了智能体所处的任务环境后，我们来探讨其核心的运行机制。智能体并非一次性完成任务，而是通过一个持续的循环与环境进行交互，这个核心机制被称为 智能体循环 (Agent Loop)。

这个循环主要包含以下几个相互关联的阶段：

  1. 感知 (Perception)：这是循环的起点。智能体通过其传感器（例如，API 的监听端口、用户输入接口）接收来自环境的输入信息。这些信息，即观察 (Observation)，既可以是用户的初始指令，也可以是上一步行动所导致的环境状态变化反馈。

  2. 思考 (Thought)：接收到观察信息后，智能体进入其核心决策阶段。对于 LLM 智能体而言，这通常是由大语言模型驱动的内部推理过程。如图所示，“思考”阶段可进一步细分为两个关键环节：

  • 规划 (Planning)：智能体基于当前的观察和其内部记忆，更新对任务和环境的理解，并制定或调整一个行动计划。这可能涉及将复杂目标分解为一系列更具体的子任务。
  • 工具选择 (Tool Selection)：根据当前计划，智能体从其可用的工具库中，选择最适合执行下一步骤的工具，并确定调用该工具所需的具体参数。
  1. 行动 (Action)：决策完成后，智能体通过其执行器（Actuators）执行具体的行动。这通常表现为调用一个选定的工具（如代码解释器、搜索引擎 API），从而对环境施加影响，意图改变环境的状态。

行动并非循环的终点。智能体的行动会引起环境 (Environment) 的状态变化 (State Change)，环境随即会产生一个新的观察 (Observation) 作为结果反馈。这个新的观察又会在下一轮循环中被智能体的感知系统捕获，形成一个持续的“感知-思考-行动-观察”的闭环。智能体正是通过不断重复这一循环，逐步推进任务，从初始状态向目标状态演进。

1.3 智能体的感知与行动

在工程实践中，为了让 LLM 能够有效驱动这个循环，我们需要一套明确的交互协议 (Interaction Protocol) 来规范其与环境之间的信息交换。

在许多现代智能体框架中，这一协议体现在对智能体每一次输出的结构化定义上。智能体的输出不再是单一的自然语言回复，而是一段遵循特定格式的文本，其中明确地展示了其内部的推理过程与最终决策。

这个结构通常包含两个核心部分：

  • Thought (思考)：这是智能体内部决策的“快照”。它以自然语言形式阐述了智能体如何分析当前情境、回顾上一步的观察结果、进行自我反思与问题分解，并最终规划出下一步的具体行动。
  • Action (行动)：这是智能体基于思考后，决定对环境施加的具体操作，通常以函数调用的形式表示。

1.4.3 Step 3 准备提示词模版

设计一个“指令模板”，告诉 LLM 它应该扮演什么角色、拥有哪些工具、以及如何格式化它的思考和行动。这是我们智能体的“说明书”，它将作为system_prompt传递给 LLM。

Code 
AGENT_SYSTEM_PROMPT <- r"(
你是一个智能旅行助手。你的任务是分析用户的请求，并使用可用工具一步步地解决问题。

# 可用工具:
- `get_weather(city)`: 查询指定城市的实时天气。
- `get_attraction(city, weather)`: 根据城市和天气搜索推荐的旅游景点。

# 行动格式:
你的回答必须严格遵循以下格式。首先是你的思考过程，然后是你要执行的具体行动，每次回复只输出一对Thought-Action：
Thought: [这里是你的思考过程和下一步计划]
Action: 你决定采取的行动，必须是以下格式之一:
- `function_name(arg_name="arg_value")`: 调用一个可用工具。
- `Finish[最终答案]`: 当你认为已经获得最终答案时。
- 当你收集到足够的信息，能够回答用户的最终问题时，你必须在Action:字段后使用 Finish[最终答案] 来输出最终答案。

请开始吧！
)"

library(httr)
library(jsonlite)

get_weather <- function(city) {

  city_enc <- URLencode(city, reserved = TRUE)
  url <- paste0("https://wttr.in/", city_enc)

  tryCatch({

    res <- GET(
      url,
      query = list(format = "j1", lang = "zh"),
      user_agent("weather-agent/0.1"),
      timeout(8)
    )

    stop_for_status(res)

    txt <- content(res, "text", encoding = "UTF-8")

    # 🔴 关键防御：不是 JSON 直接拦截
    if (!startsWith(trimws(txt), "{")) {
      stop("返回内容不是 JSON，可能是城市名无法识别或服务异常")
    }

    data <- fromJSON(txt, simplifyVector = FALSE)

    current <- data$current_condition[[1]]
    desc <- current$weatherDesc[[1]]$value
    temp <- current$temp_C

    paste0(city, " 当前天气：", desc, "，气温 ", temp, "°C")

  }, error = function(e) {
    paste("错误：查询天气失败 -", e$message)
  })
}

get_attraction <- function(city, weather) {

  # 1️⃣ 标准化输入
  city <- trimws(city)
  weather <- tolower(weather)

  # 2️⃣ 天气 → 出行类型
  scene <- if (grepl("雨|snow|雪|storm", weather)) {
    "indoor"
  } else if (grepl("晴|sunny|clear", weather)) {
    "outdoor"
  } else {
    "mixed"
  }

  # 3️⃣ 内置「城市 → 景点库」
  attraction_db <- list(

    "北京" = list(
      outdoor = c("颐和园", "天坛公园", "八达岭长城"),
      mixed   = c("故宫", "什刹海"),
      indoor  = c("中国国家博物馆", "中国美术馆")
    ),

    "上海" = list(
      outdoor = c("外滩", "世纪公园"),
      mixed   = c("豫园", "新天地"),
      indoor  = c("上海博物馆", "中华艺术宫")
    ),

    "长沙" = list(
      outdoor = c("岳麓山", "橘子洲头"),
      mixed   = c("太平街", "坡子街"),
      indoor  = c("湖南省博物馆")
    ),

    "杭州" = list(
      outdoor = c("西湖", "九溪十八涧"),
      mixed   = c("灵隐寺"),
      indoor  = c("浙江省博物馆")
    )
  )

  # 4️⃣ 城市容错（中英文）
  city_map <- c(
    "Beijing"   = "北京",
    "Shanghai" = "上海",
    "Changsha" = "长沙",
    "Hangzhou" = "杭州"
  )

  if (city %in% names(city_map)) {
    city <- city_map[[city]]
  }

  # 5️⃣ 查找城市
  if (!city %in% names(attraction_db)) {
    return(
      paste0(
        "我暂时没有 ", city,
        " 的详细景点数据。建议选择当地知名公园、博物馆或历史街区游览。"
      )
    )
  }

  # 6️⃣ 输出推荐
  recs <- attraction_db[[city]][[scene]]

  paste0(
    city, " 当前天气为「", weather, "」，",
    "更适合游览【",
    ifelse(scene == "outdoor", "户外",
           ifelse(scene == "indoor", "室内", "灵活选择")),
    "景点】。\n推荐景点：",
    paste(recs, collapse = "、")
  )
}

1.4.5 step 5 引入大语言模型

要提供三个信息：API_KEY、BASE_URL 和 MODEL_ID，具体值取决于您使用的服务商（如 OpenAI 官方、Azure、或 Ollama 等本地模型）

Code 
library(httr)
library(jsonlite)

OpenAICompatibleClient <- function(model, api_key = "ollama", base_url) {

  client <- list(
    model = model,
    api_key = api_key,
    base_url = base_url
  )

  client$generate <- function(prompt, system_prompt) {

  message("正在调用大语言模型...")

  body <- list(
    model = client$model,
    messages = list(
      list(role = "system", content = system_prompt),
      list(role = "user",   content = prompt)
    ),
    stream = FALSE
  )

  res <- tryCatch({
    POST(
      url = paste0(client$base_url, "/v1/chat/completions"),
      add_headers(
        Authorization = paste("Bearer", client$api_key),
        `Content-Type` = "application/json"
      ),
      body = toJSON(body, auto_unbox = TRUE),
      encode = "raw",
      timeout(120)
    )
  }, error = function(e) {
    message("调用 LLM API 时发生错误: ", e$message)
    return(NULL)
  })

  if (is.null(res) || status_code(res) != 200) {
    return("错误: 调用语言模型服务时出错。")
  }

  # 🔴 关键：关闭简化
  data <- fromJSON(
    content(res, "text", encoding = "UTF-8"),
    simplifyVector = FALSE
  )

  answer <- tryCatch({

    # Ollama / OpenAI 兼容
    if (!is.null(data$choices[[1]]$message$content)) {
      data$choices[[1]]$message$content
    } else if (!is.null(data$choices[[1]]$text)) {
      data$choices[[1]]$text
    } else {
      stop("未找到模型输出字段")
    }

  }, error = function(e) {
    paste("错误: 无法解析模型返回结果 -", e$message)
  })

  message("大语言模型响应成功。")
  answer
}

  class(client) <- "OpenAICompatibleClient"
  client
}

# 抓去action 
extract_last_action <- function(text) {
  actions <- str_match_all(text, "Action:\\s*(.*)")[[1]]
  if (nrow(actions) == 0) return(NA)
  str_trim(tail(actions[, 2], 1))
}

is_finish <- function(action_str) {
  
  str_starts(action_str, "Finish")
}
normalize_action <- function(action_str) {
  action_str |>
    str_trim() |>                # 去首尾空白
    str_remove("^`+") |>         # 去前面的 `
    str_remove("`+$")            # 去后面的 `
}

extract_finish <- function(action_str) {
  str_match(action_str, "Finish\\[(.*)\\]")[1, 2]
}

  # 3.3 解析 Action
  action_str <- extract_last_action(res)
  action_str <- normalize_action(action_str)
   if (is_finish(action_str)) {
  final_answer <- extract_finish(action_str)
  writeLines(final_answer)
  break
}
  
  if (is.na(action_str)) {
  observation_str <- "Observation: 错误: 未能解析到 Action。"
  prompt_history <- c(prompt_history, observation_str)
  next
}




  # --- 解析工具名与参数 ---
  tool_name <- str_match(action_str, "(\\w+)\\(")[1, 2]
  args_str  <- str_match(action_str, "\\((.*)\\)")[1, 2]

  kwargs <- list()
  arg_matches <- str_match_all(args_str, '(\\w+)="([^"]*)"')[[1]]
  if (nrow(arg_matches) > 0) {
    for (j in seq_len(nrow(arg_matches))) {
      kwargs[[arg_matches[j, 2]]] <- arg_matches[j, 3]
    }
  }

  # --- 执行工具 ---
  if (tool_name %in% names(available_tools)) {
    fn <- available_tools[[tool_name]]$fn
    observation <- tryCatch(
      do.call(fn, kwargs),
      error = function(e) paste("工具执行错误:", e$message)
    )
  } else {
    observation <- paste0("错误: 未定义的工具 '", tool_name, "'")
  }

  # 3.4 记录 Observation
  observation_str <- paste0("Observation: ", observation)
  cat(observation_str, "\n", strrep("=", 40), "\n")
  prompt_history <- c(prompt_history, observation_str)
}

这个简单的旅行助手案例，集中演示了基于Thought-Action-Observation范式的智能体所具备的四项基本能力：任务分解、工具调用、上下文理解和结果合成。正是通过这个循环的不断迭代，智能体才得以将一个模糊的用户意图，转化为一系列具体、可执行的步骤，并最终达成目标。

1.5 技术要点拆解

整个 Agent 被拆解为 5 个清晰职责层：

  1. Prompt 设计层（AGENT_SYSTEM_PROMPT）
  2. 模型调用层（OpenAI-compatible Client）
  3. 文本清洗层（strip / normalize）
  4. Action 解析与执行层

1.5.1 Prompt 必须是结构化协议，而不是“提示文本”

Prompt 在 Agent 中不是提示词，而是「通信协议」, Agent 的 Action 是从模型输出中“解析”出来的, 果输出格式不稳定：正则必炸, Agent 无法继续. 必须明确 Thought: / Action: 标签.明确 Finish[…] 作为终止信号

因此, 必须良好设计prompt,Prompt ≠ 自然语言,Prompt = 输出语法约束,Agent 的 Prompt 设计本质是 协议设计.这是 Agent 与 ChatBot 的第一道分水岭。

1.5.2 不要试图解析“完整思考链”

只执行“最后一个可执行 Action”. 因为, LLM 输出是,脏文本,会重复 Thought,会夹杂说明、假设、Markdown

1.5.3 必须有一层「文本归一化（Normalization）」

LLM 的输出永远不干净,所以,解析前一定要 normalize

1.5.4 Finish[…] 是一个显式状态机信号

Finish[…] ≠ 普通文本,它是一个 状态转移信号,Agent 不是“问一次答一次”,Agent 是多步状态机,Finish = 终止态,这是 Agent 与普通 LLM 调用的第二个分水岭。

1.5.5 Observation 回填 = 外部世界注入

Tool 的返回值不是给用户看的，而是给模型“看的”.LLM 本身不“知道世界”世界状态通过：

  1. Tool → Observation → Prompt History
  2. 被重新注入模型上下文

Agent = LLM + 外部世界的闭环。

1.5.6 Prompt History 是 Agent 的「短期记忆」

Agent 是： - 多轮推理 - 有状态的系统

prompt_history 就是, 最小形态的 memory buffer

1.6 智能体应用的写作模式

协作模式主要分为两种：一种是作为高效工具，深度融入我们的工作流；另一种则是作为自主的协作者，与其他智能体协作完成复杂目标。

1.6.1 作为开发者工具的智能体

智能体被深度集成到开发者的工作流中，作为一种强大的辅助工具。它增强而非取代开发者的角色，通过自动化处理繁琐、重复的任务，让开发者能更专注于创造性的核心工作。这种人机协同的方式，极大地提升了软件开发的效率与质量。

市场上涌现了多款优秀的 AI 编程辅助工具，它们虽然均能提升开发效率，但在实现路径和功能侧重上各有千秋：

  • GitHubCopilot
  • Claude Code
  • Trae
  • Cursor

AI 正在深度融入软件开发的全生命周期，通过构建高效的人机协同工作流，深刻地重塑着软件工程的效率边界与开发范式。

1.6.2 作为自主协作者的智能体

这种模式下，我们不再是手把手地指导 AI 完成每一步，而是将一个高层级的目标委托给它。智能体会像一个真正的项目成员一样，独立地进行规划、推理、执行和反思，直到最终交付成果。这种从助手到协作者的转变，使得 LLM 智能体更深的进入了大众的视野。它标志着我们与 AI 的关系从“命令-执行”演变为“目标-委托”。智能体不再是被动的工具，而是主动的目标追求者。

它们的架构范式大致可以归纳为几个主流方向：

  • 单智能体自主循环：这是早期的典型范式，如 AgentGPT 所代表的模式。其核心是一个通用智能体通过“思考-规划-执行-反思”的闭环，不断进行自我提示和迭代，以完成一个开放式的高层级目标。
  • 多智能体协作：这是当前最主流的探索方向，旨在通过模拟人类团队的协作模式来解决复杂问题。它又可细分为不同模式： 角色扮演式对话：如 CAMEL 框架，通过为两个智能体（例如，“程序员”和“产品经理”）设定明确的角色和沟通协议，让它们在一个结构化的对话中协同完成任务。 组织化工作流：如 MetaGPT 和 CrewAI，它们模拟一个分工明确的“虚拟团队”（如软件公司或咨询小组）。每个智能体都有预设的职责和工作流程（SOP），通过层级化或顺序化的方式协作，产出高质量的复杂成果（如完整的代码库或研究报告）。AutoGen 和 AgentScope 则提供了更灵活的对话模式，允许开发者自定义智能体间的复杂交互网络。
  • 高级控制流架构：诸如 LangGraph 等框架，则更侧重于为智能体提供更强大的底层工程基础。它将智能体的执行过程建模为状态图（State Graph），从而能更灵活、更可靠地实现循环、分支、回溯以及人工介入等复杂流程。 这些不同的架构范式，共同推动着自主智能体从理论构想走向更广泛的实际应用，使其有能力应对日益复杂的真实世界任务。在我们的后续章节中，也会感受不同类型框架之间的差异和优势。

1.6.3 Workflow 和 Agent 的差异

Workflow 是让 AI 按部就班地执行指令，而 Agent 则是赋予 AI 自由度去自主达成目标。

工作流是一种传统的自动化范式，其核心是对一系列任务或步骤进行预先定义的、结构化的编排。它本质上是一个精确的、静态的流程图，规定了在何种条件下、以何种顺序执行哪些操作。

于大型语言模型的智能体是一个具备自主性的、以目标为导向的系统。上文就是一个例子:

我们向它下达一个新指令，例如：“你好，请帮我查询一下今天北京的天气，然后根据天气推荐一个合适的旅游景点。” 它的处理过程充分展现了其自主性：

  • 规划与工具调用： Agent 首先会把任务拆解为两个步骤：① 查询天气；② 基于天气推荐景点。随即，它会自主选择并调用“天气查询 API”，并将“北京”作为参数传入。
  • 推理与决策： 假设 API 返回结果为“晴朗，微风”。Agent 的 LLM 大脑会基于这个信息进行推理：“晴天适合户外活动”。接着，它会根据这个判断，在它的知识库或通过搜索引擎这个工具中，筛选出北京的户外景点，如故宫、颐和园、天坛公园等。
  • 生成结果： 最后，Agent 会综合信息，给出一个完整的、人性化的回答

在这个过程中，没有任何写死的if天气=晴天 then 推荐某个地点的规则。如果天气是“雨天”，Agent 会自主推理并推荐室内场所。这种基于实时信息进行动态推理和决策的能力，正是 Agent 的核心价值所在。
