4  Construction of the classical agent paradigm

一个现代的智能体，其核心能力在于能将大语言模型的推理能力与外部世界联通。它能够自主地理解用户意图、拆解复杂任务，并通过调用代码解释器、搜索引擎、API等一系列“工具”，来获取信息、执行操作，最终达成目标。 然而，智能体并非万能，它同样面临着来自大模型本身的“幻觉”问题、在复杂任务中可能陷入推理循环、以及对工具的错误使用等挑战，这些也构成了智能体的能力边界。

最具代表性的三种:

  • ReAct (Reasoning and Acting)： 一种将“思考”和“行动”紧密结合的范式，让智能体边想边做，动态调整。
  • Plan-and-Solve： 一种“三思而后行”的范式，智能体首先生成一个完整的行动计划，然后严格执行。
  • Reflection： 一种赋予智能体“反思”能力的范式，通过自我批判和修正来优化结果。

4.2 ReAct

在完成 LLM 客户端准备后，将构建第一个也是最经典的智能体范式 ReAct（Reason + Act）。该方法由 Shunyu Yao 于 2022 年提出[1]，其核心思想是模拟人类的问题求解过程，将 推理（Reasoning） 与 行动（Acting） 显式结合，形成持续的 “思考–行动–观察” 循环。

4.2.1 ReAct 的工作流程

在 ReAct 出现之前，主流智能体方法主要分为两类：

  • “纯思考”型：如思维链（Chain-of-Thought），能够引导模型进行复杂推理，但无法与外部环境交互，容易产生事实幻觉。

  • “纯行动”型：模型直接给出要执行的动作，但缺乏整体规划与纠错能力。

ReAct 的关键创新在于将思考与行动视为相互促进的过程：思考指导行动，行动结果反过来修正思考。为此，ReAct 通过特定的提示工程，约束模型每一步遵循固定流程：

  • Thought（思考）：分析当前状态，拆解任务，规划下一步或反思结果。
  • Action（行动）：执行具体操作，通常是调用外部工具，如 Search[‘华为最新款手机’]。
  • Observation（观察）：获取行动返回的结果，如搜索摘要或 API 输出。

智能体不断循环 Thought → Action → Observation，将新的观察结果加入上下文，直到在 Thought 中确认已得到最终答案并输出。该机制形成协同效应：推理提升行动的目的性，行动为推理提供可靠的事实依据。

我们可以将这个过程形式化地表达出来，如图 4.1 所示。具体来说，在每个时间步 \(t\)，智能体的策略（即大语言模型 \(\pi\)）会根据初始问题 \(q\) 和之前所有步骤的“行动-观察”历史轨迹 \(\big((a_1, o_1), \ldots, (a_{t-1}, o_{t-1})\big)\)， 来生成当前的思考 \(th_t\) 和行动 \(a_t\)：

\[ (th_t, a_t) = \pi\!\left( q, (a_1, o_1), \ldots, (a_{t-1}, o_{t-1}) \right) \]

随后，环境中的工具 \(T\) 会执行行动 \(a_t\)，并返回一个新的观察结果 \(o_t\)：

\[ o_t = T(a_t) \]

这个循环不断进行，将新的 \((a_t, o_t)\) 对追加到历史中，直到模型在思考 \(th_t\) 中判断任务已完成。

该机制尤其适用于以下场景：

  • 依赖外部知识的任务：如获取实时信息（天气、新闻、股价）或检索专业领域资料。
  • 需要精确计算的任务：将数学运算交由计算器等工具，避免 LLM 的计算误差。
  • 需要 API 交互的任务：如数据库操作或调用外部服务接口完成特定功能。

因此，我们将构建一个具备外部工具调用能力的 ReAct 智能体，用于回答仅凭模型自身知识库难以直接解决的问题。例如：“华为最新的手机是哪一款？它的主要卖点是什么？” 该问题要求智能体识别信息不足，主动上网检索，并基于工具返回结果进行归纳总结。

4.2.2 工具的定义与实现

如果说大语言模型是智能体的大脑，那么工具 (Tools) 就是其与外部世界交互的“手和脚”。为了让ReAct范式能够真正解决我们设定的问题，智能体需要具备调用外部工具的能力。

4.2.2.1 （1）实现搜索工具的核心逻辑

一个良好定义的工具应包含以下三个核心要素：

  • 名称 (Name)： 一个简洁、唯一的标识符，供智能体在 Action 中调用，例如 Search。
  • 描述 (Description)： 一段清晰的自然语言描述，说明这个工具的用途。这是整个机制中最关键的部分，因为大语言模型会依赖这段描述来判断何时使用哪个工具。
  • 执行逻辑 (Execution Logic)： 真正执行任务的函数或方法。

4.2.2.2 （2）构建通用的工具执行器

ToolExecutor 本质上是在做三件事：

  1. 工具注册（Registry）
  2. 工具调度（Dispatch）
  3. 工具能力暴露（Tool List for Agent）
Code 
ToolExecutor <- function() {

  tools <- list()

  list(

    # --- 注册工具 ---
    registerTool = function(name, description, func) {

      if (!is.character(name) || name == "") {
        stop("工具名必须是非空字符串")
      }

      if (name %in% names(tools)) {
        message(sprintf("警告：工具 '%s' 已存在，将被覆盖。", name))
      }

      tools[[name]] <<- list(
        description = description,
        func = func
      )

      message(sprintf("工具 '%s' 已注册。", name))
    },

    # --- 获取工具函数 ---
    getTool = function(name) {
      if (!name %in% names(tools)) {
        return(NULL)
      }
      tools[[name]]$func
    },

    # --- 获取所有工具描述 ---
    getAvailableTools = function() {
      if (length(tools) == 0) {
        return("（当前无可用工具）")
      }

      paste(
        sapply(names(tools), function(name) {
          sprintf("- %s: %s", name, tools[[name]]$description)
        }),
        collapse = "\n"
      )
    },

    # --- （可选）内部状态，用于调试 ---
    .tools = function() tools
  )
}

- search_fact

================================================
【工具调用协议（必须遵守）】

Action: search_fact(query="...")

================================================
【FACT 收敛规则（非常重要）】

当 Observation 中出现以 "FACT:" 开头的内容时：

这表示你已经获得了回答用户问题所需的全部关键信息。

你【必须】在下一步直接输出：

Action: Finish[完整、可直接给用户看的中文回答]

禁止：
- 再调用任何工具
- 再输出 Thought
- 延迟 Finish

================================================
【输出格式（每一步必须一致）】

Thought: ...
Action: ...

================================================
违反任一规则，视为任务失败。

'

该模板规范了智能体与 LLM 的交互方式，主要包括以下要素：

  • 角色定义：设定 LLM 为“具备外部工具调用能力的智能助手”，明确其职责。
  • 工具清单（{tools}）：告知 LLM 可使用的外部工具能力边界。
  • 格式规约（Thought / Action）：核心约束，强制输出结构化，便于代码精确解析与控制。
  • 动态上下文（{question} / {history}）：注入用户问题与累积交互历史，确保模型基于完整上下文决策。

4.2.3.2 （2）核心循环的实现

ReActAgent 的核心是一个循环，它不断地“格式化提示词 -> 调用LLM -> 执行动作 -> 整合结果”，直到任务完成或达到最大步数限制。

Code 
library(stringr)

# ===============================
# Action 解析与规范化
# ===============================

extract_last_action <- function(text) {
  actions <- str_match_all(text, "Action:\\s*(.*)")[[1]]
  if (is.null(actions) || nrow(actions) == 0) return(NA_character_)
  str_trim(tail(actions[, 2], 1))
}

is_finish <- function(action_str) {
  str_starts(action_str, "Finish")
}

normalize_action <- function(action_str) {

  if (is.na(action_str)) return(NA_character_)

  action_str <- str_trim(action_str)
  action_str <- strsplit(action_str, "\n")[[1]][1]

  action_str <- str_remove(action_str, "^`+")
  action_str <- str_remove(action_str, "`+$")
  action_str <- str_replace_all(action_str, "```", "")

  str_trim(action_str)
}

extract_finish <- function(action_str) {
  if (is.na(action_str)) return(NA_character_)
  m <- str_match(action_str, "^Finish\\[(.*)\\]$")
  if (is.na(m[1, 2])) return(NA_character_)
  str_trim(m[1, 2])
}

# ===============================
# ReAct 主循环
# ===============================

run_react_agent <- function(
  user_prompt,
  llm,
  executor,
  system_prompt,
  max_steps = 5
) {

  history <- c(paste0("用户请求: ", user_prompt))

  cat("用户输入:", user_prompt, "\n")
  cat(strrep("=", 40), "\n")

  for (step in seq_len(max_steps)) {

    cat(sprintf("\n--- Step %d ---\n\n", step))

    full_prompt <- paste(history, collapse = "\n")

    llm_output <- llm$generate(
      prompt = full_prompt,
      system_prompt = system_prompt
    )

    llm_output <- strip_think(llm_output)

    cat("模型输出:\n")
    cat(llm_output, "\n\n")

    history <- c(history, llm_output)

    # --- Action 解析 ---
    action_raw <- extract_last_action(llm_output)
    action_str <- normalize_action(action_raw)

    if (is.na(action_str)) {
      history <- c(history, "Observation: 无法解析 Action")
      next
    }

    # --- 模型主动 Finish ---
    if (is_finish(action_str)) {

      final_answer <- extract_finish(action_str)

      if (!is.na(final_answer)) {
        cat("✅ 任务完成（模型 Finish）：\n")
        cat(final_answer, "\n")
        return(final_answer)
      }

      history <- c(history, "Observation: Finish 内容无效，请重新给出完整中文回答。")
      next
    }

    # --- 工具调用 ---
    tool_name <- str_match(action_str, "(\\w+)\\(")[1, 2]
    args_str  <- str_match(action_str, "\\((.*)\\)")[1, 2]

    args <- list()
    arg_matches <- str_match_all(args_str, '(\\w+)="([^"]*)"')[[1]]
    if (!is.null(arg_matches) && nrow(arg_matches) > 0) {
      for (i in seq_len(nrow(arg_matches))) {
        args[[arg_matches[i, 2]]] <- arg_matches[i, 3]
      }
    }

    tool_fn <- executor$getTool(tool_name)

    if (is.null(tool_fn)) {
      observation <- paste("错误：未知工具", tool_name)
    } else {
      observation <- tryCatch(
        do.call(tool_fn, args),
        error = function(e) paste("工具执行错误:", e$message)
      )
    }

    obs_str <- paste0("Observation: ", observation)
    cat(obs_str, "\n")
    cat(strrep("-", 40), "\n")

    history <- c(history, obs_str)

    # =====================================================
    # ⭐ FACT → 强制模型 Finish（核心修改点）
    # =====================================================
    if (grepl("^FACT:", observation)) {

      cat("🧠 执行器判断：已获得 FACT，要求模型给出 Finish。\n")

      history <- c(
        history,
        "系统提示：你已经获得 FACT。",
        "请立刻使用 Action: Finish[完整中文回答]。",
        "不要再调用工具，不要输出 Thought。"
      )

      next
    }
  }

  # --- 最终兜底（极少触发） ---
  cat("⚠️ 达到最大步数，模型未 Finish，执行器兜底。\n")

  fact <- history[grepl("^Observation: FACT:", history)]
  if (length(fact) > 0) {
    fact_body <- sub("^Observation: FACT:\\s*", "", tail(fact, 1))
    final_text <- paste0(
      fact_body,
      "\n\n通俗理解：智能体就是一个能感知、会判断、能行动的系统，目标是把事情完成。"
    )
    cat(final_text, "\n")
    return(final_text)
  }

  invisible(NULL)
}

4.2.4 ReAct 的特点、局限性与调试技巧

通过亲手实现 ReAct 智能体，不仅可以掌握其运行流程，也能更深入理解其内在机制。任何技术范式都有优势与不足，下面对 ReAct 作一总结。

4.2.4.1 （1）ReAct 的主要特点

  • 高可解释性：通过 Thought 链可清晰追踪每一步决策依据，便于理解、信任与调试。
  • 动态规划与纠错：采用“边走边看”的方式，根据 Observation 实时调整后续 Thought 与 Action。
  • 工具协同能力：将 LLM 的推理与外部工具的执行能力结合，弥补知识时效性与计算准确性的不足。

4.2.4.2 （2）ReAct 的固有局限性

  • 强依赖 LLM 能力：推理、指令遵循或格式输出能力不足，都会导致流程失败。
  • 执行效率偏低：多轮 LLM 调用带来更高的时延与成本，复杂任务尤为明显。
  • 提示词脆弱性：机制依赖精心设计的模板，细微改动或模型差异都可能影响稳定性。
  • 易陷入局部最优：缺乏全局规划，可能因短期 Observation 做出非最优决策，甚至循环停滞。

4.2.4.3 （3）调试技巧

  • 检查完整提示词：打印包含历史记录的最终提示，追溯决策来源。
  • 分析原始输出：解析失败时查看未处理文本，区分模型问题或解析逻辑问题。
  • 验证工具交互：确认 tool_input 与 observation 的格式是否符合预期。
  • 引入示例（Few-shot）：加入完整成功案例，引导模型遵循流程。
  • 更换模型或参数：尝试更强模型或将 temperature 设为 0，提高稳定性。

4.3 Plan-and-Solve

Plan-and-Solve 范式将任务处理清晰地划分为两个阶段：先 规划（Plan），再 执行（Solve）。

如果说 ReAct 像一名根据现场线索不断调整方向的侦探，那么 Plan-and-Solve 更像一位建筑师——在动工前先完成完整蓝图，然后严格按计划实施。实际上，当前许多大模型工具的 Agent 模式都融入了这一设计思想。

4.3.1 Plan-and-Solve 的工作原理

Plan-and-Solve Prompting 由 Lei Wang 于 2023 年提出[2]，旨在解决思维链在多步骤复杂任务中易“跑偏”的问题。

与 ReAct 在每一步融合思考与行动不同，Plan-and-Solve 将流程解耦为两个阶段：

  • 规划阶段（Planning Phase）：接收完整问题后，先对任务进行拆解，生成清晰的分步行动计划。该计划本身由一次 LLM 调用产生。
  • 执行阶段（Solving Phase）：在获得计划后，严格按步骤执行。每一步可对应一次 LLM 调用或对中间结果的处理，直至完成所有步骤并得到最终答案。

这种“先谋后动”的策略提升了复杂任务中的目标一致性，降低了中途偏离方向的风险。

我们可以将这个两阶段过程进行形式化表达。首先，规划模型 \(\pi_{\text{plan}}\) 根据原始问题 \(q\) 生成一个包含 \(n\) 个步骤的计划 \(P = (p_1, p_2, \ldots, p_n)\)：

\[ P = \pi_{\text{plan}}(q) \]

随后，在执行阶段，执行模型 \(\pi_{\text{solve}}\) 会逐一完成计划中的步骤。对于第 \(i\) 个步骤，其解决方案 \(s_i\) 的生成会同时依赖于原始问题 \(q\)、完整计划 \(P\) 以及之前所有步骤的执行结果 \((s_1, \ldots, s_{i-1})\)：

\[ s_i = \pi_{\text{solve}} \left( q, P, (s_1, \ldots, s_{i-1}) \right) \]

最终的答案就是最后一个步骤的执行结果 \(s_n\)。

Plan-and-Solve 特别适合结构清晰、可明确拆解的复杂任务，例如：

  • 多步数学应用题：先规划计算步骤，再逐步求解。
  • 多源信息整合的报告撰写：先确定报告结构（引言、各数据来源、总结），再逐项填充内容。
  • 代码生成任务：先设计函数、类与模块结构，再逐步实现。

4.3.2 规划阶段

为突出 Plan-and-Solve 在结构化推理任务中的优势，我们将不依赖外部工具，而是通过提示词设计完成一次推理。

这类任务的关键在于：答案无法通过一次查询或单步计算得到，必须先将问题拆解为逻辑连贯的子步骤，再按顺序求解，正好契合 Plan-and-Solve “先规划、后执行”的能力。

目标问题为： “水果店周一卖出 15 个苹果；周二是周一的两倍；周三比周二少 5 个。三天一共卖出多少个苹果？”

虽然问题本身不难，但包含清晰的推理链条，可作为模板迁移到更复杂的逻辑难题：当模型难以稳定给出高质量推理时，可用该模式设计 Agent 来提升可靠性。智能体需要完成：

  • 规划阶段：将问题拆解为三步（求周二销量、求周三销量、求三天总和）。
  • 执行阶段：严格按计划逐步计算，并将每一步结果作为下一步输入，得到最终总数。

规划阶段的目标是让模型基于原始问题输出结构化的分步计划，便于代码解析与顺序执行。因此，提示词应明确模型角色与任务，并提供清晰的输出格式示例。

我们用一个足够真实、但不复杂的问题：

问题, 一家公司想引入 AI 自动化客服流程， 请分析： - 是否适合自动化 - 主要风险 - 实施步骤

Code 
PLAN_PROTOCOL <- function(question) {
  paste0(
    "你是一个【规划器】。\n\n",
    "你的职责是：为给定问题生成一个【可执行的解决计划】。\n\n",
    "规划原则：\n",
    "1. 每一步都是必要的，不允许冗余\n",
    "2. 步骤必须是线性的、可顺序执行的\n",
    "3. 每一步描述【要做什么】，而不是结论\n",
    "4. 不进行任何实际分析或判断\n",
    "5. 不回答问题本身\n\n",
    "输出格式：\n",
    "- 使用编号列表（1. 2. 3. ...）\n",
    "- 每一步一句话\n\n",
    "问题：\n",
    question
  )
}


ACTION_PROMPT <- function(step, plan, question) {
  paste0(
    "你是一个【执行器】。\n\n",
    "你必须严格执行给定计划中的【当前步骤】。\n\n",
    "全局约束：\n",
    "- 不允许新增、删除或重排步骤\n",
    "- 不允许提前或总结后续步骤\n\n",
    "完整计划：\n",
    plan, "\n\n",
    "当前步骤：\n",
    step, "\n\n",
    "原始问题：\n",
    question, "\n\n",
    "请只完成【当前步骤】的内容。"
  )
}


extract_steps <- function(plan_text) {
  lines <- unlist(strsplit(plan_text, "\n"))

  steps <- grep(
    "^\\s*[-•]?\\s*\\d+\\.",
    lines,
    value = TRUE
  )

  trimws(steps)
}
Code 
plan_and_solve_loop <- function(
  question,
  llm,
  plan_temperature  = 0.2,
  action_temperature = 0.3,
  verbose = TRUE
) {

  ## ---------- PLAN ----------
  plan_prompt <- PLAN_PROTOCOL(question)
  plan_text <- llm$generate(
  prompt = plan_prompt,
  system_prompt = "You are a planning agent."
  )
 
  steps <- extract_steps(plan_text)

  if (verbose) {
    cat("\n===== PLAN =====\n")
    cat(plan_text, "\n")
  }

  ## ---------- ACTION LOOP ----------
  results <- list()

  for (i in seq_along(steps)) {
    step <- steps[[i]]

    if (verbose) {
      cat("\n--- Executing Step", i, "---\n")
      cat(step, "\n")
    }

    action_prompt <- ACTION_PROMPT(
      step     = step,
      plan     = plan_text,
      question = question
    )

    action_output <- llm$generate(
      prompt = action_prompt,
      system_prompt = "You are an execution agent."
    )

    results[[i]] <- list(
      step   = step,
      output = trimws(action_output)
    )

    if (verbose) {
      cat(results[[i]]$output, "\n")
    }
  }

  ## ---------- RETURN ----------
  invisible(list(
    question = question,
    plan     = plan_text,
    steps    = results
  ))
}

4.4 Reflection

4.4.1 Reflection 机制的核心思想

Reflection 机制源于人类的学习方式：完成初稿后校对，解题后验算。该思想在多项研究中体现，如 Shinn、Noah 于 2023 年提出的 Reflexion 框架[3]。其流程可概括为 执行 → 反思 → 优化 的三步循环。

  1. 执行（Execution）：智能体先采用既有方法（如 ReAct 或 Plan-and-Solve）完成任务，生成初步方案或行动轨迹，相当于“初稿”。
  2. 反思（Reflection）：随后由独立或带特殊提示的模型充当“评审员”，从多个维度审视初稿，包括：
  • 事实性错误
  • 逻辑漏洞
  • 效率问题
  • 信息遗漏 并输出结构化反馈，指出问题与改进建议。
  1. 优化（Refinement）：将初稿与反馈一并作为上下文，再次调用模型进行修正，生成更完善的“修订稿”。

与前两种范式相比，Reflection 的核心价值体现在：

  • 内置纠错机制：为智能体提供内部反馈回路，不再完全依赖外部 Observation，可修正更高层次的逻辑与策略错误。
  • 持续优化能力：将一次性执行转变为迭代优化过程，显著提升复杂任务的成功率与结果质量。
  • 短期记忆构建：完整的“执行–反思–优化”轨迹形成经验记录，使智能体既保留最终结果，也保留改进路径；该记忆还可扩展为多模态，用于反思与修正代码、图像等输出，为更强大的多模态智能体奠定基础。

reflection_agent <- function(
  question,
  llm,
  verbose = TRUE
) {

  ## ---------- ACT ----------
  answer_1 <- llm_call(
    llm,
    prompt = ACTOR_PROMPT(question),
    system_prompt = "You are an answering agent."
  )

  if (verbose) {
    cat("\n===== INITIAL ANSWER =====\n")
    cat(answer_1, "\n")
  }

  ## ---------- REFLECT ----------
  reflection <- llm_call(
    llm,
    prompt = REFLECTION_PROMPT(question, answer_1),
    system_prompt = "You are a reflection agent."
  )

  if (verbose) {
    cat("\n===== REFLECTION =====\n")
    cat(reflection, "\n")
  }

  ## ---------- REWRITE ----------
  answer_2 <- llm_call(
    llm,
    prompt = REWRITE_PROMPT(question, answer_1, reflection),
    system_prompt = "You are a rewriting agent."
  )

  if (verbose) {
    cat("\n===== FINAL ANSWER =====\n")
    cat(answer_2, "\n")
  }

  invisible(list(
    question        = question,
    initial_answer  = answer_1,
    reflection      = reflection,
    final_answer    = answer_2
  ))
}

4.4.2 Reflection 机制的成本与收益分析

尽管 Reflection 能显著提升任务质量，但其效果建立在额外成本之上，实际应用中需权衡取舍。

4.4.2.1 （1）主要成本

  • 模型调用开销增加：每轮迭代至少多出两次模型调用（反思与优化），迭代次数增加会显著放大 API 成本与算力消耗。
  • 任务延迟上升：反思与优化需串行执行，整体耗时明显增长，不适合高实时性场景。
  • 提示工程复杂化：需为执行、反思与优化分别设计高质量提示词，开发与调试成本更高。

4.4.2.2 （2）核心收益

  • 方案质量跃迁：可将“可用方案”迭代为“高质量方案”，在效率、严谨性与性能上显著提升。
  • 鲁棒性与可靠性增强：通过内部纠错，减少逻辑漏洞、事实错误与边界问题，提高结果可信度。

4.4.2.3 （3）适用场景权衡

Reflection 本质上是一种 “以成本换质量” 的策略，适合对准确性与可靠性要求极高、对实时性要求较低的场景，例如：

  • 关键业务代码或技术报告生成
  • 科学研究中的复杂逻辑推演
  • 深度分析与规划型决策支持系统

若场景强调快速响应或“基本正确”即可满足需求，则更轻量的 ReAct 或 Plan-and-Solve 往往更具性价比。
